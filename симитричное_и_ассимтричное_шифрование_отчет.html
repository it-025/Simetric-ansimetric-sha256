1. Контроль целостности (хеш SHA-256)

1.1. Создание файла и первый хеш

echo "Отчёт по практике №3" > ~/report.txt
sha256sum ~/report.txt

Получен исходный отпечаток:

Состояние файлаSHA-256
Исходный report.txt f115f1f07ccf274f6d28a6624a4d9d958c2d6c2504e0a971803b2bae3177fab9

1.2. Изменение файла на один символ

echo "." >> ~/report.txt
sha256sum ~/report.txt

Добавлена всего одна точка в конец файла. Хеш изменился полностью:

Состояние файлаSHA-256
После добавления «.» a0e2acbb38a17eec872cd1152bb76baeeb9bda0a33e1394e7d6d32b5b437aa8f
Вывод. Минимальное изменение входных данных (один байт) приводит к лавинному изменению хеша: совпадений в символах практически нет. Это и есть свойство криптографической хеш-функции, используемое для контроля целостности.

1.3. Сравнение

f115f1f07ccf274f6d28a6624a4d9d958c2d6c2504e0a971803b2bae3177fab9  /home/kali/report.txt
a0e2acbb38a17eec872cd1152bb76baeeb9bda0a33e1394e7d6d32b5b437aa8f  /home/kali/report.txt

Отпечатки не совпадают ни в одном символе — целостность нарушена, файл изменён.

2. Симметричное шифрование (AES-256-CBC)

2.1. Шифрование

openssl enc -aes-256-cbc -pbkdf2 -salt -in ~/report.txt -out ~/report.enc
enter AES-256-CBC encryption password:
Verifying - enter AES-256-CBC encryption password:
  • -aes-256-cbc — алгоритм AES с ключом 256 бит в режиме CBC;
  • -pbkdf2 — вывод ключа из пароля по PBKDF2 (защита от перебора);
  • -salt — случайная соль в начало файла;
  • пароль вводится интерактивно и не отображается.

2.2. Просмотр зашифрованного файла

Содержимое нечитаемо — это бинарные данные. Видны заголовок Salted__ и случайные байты шифротекста. скриншот содержимого

2.3. Расшифровка тем же паролем

openssl enc -aes-256-cbc -pbkdf2 -d -in ~/report.enc -out ~/report_dec.txt
enter AES-256-CBC decryption password:

diff ~/report.txt ~/report_dec.txt
(пустой вывод — различий нет)

diff не вывел ничего → расшифрованный файл побайтово совпадает с исходным. Расшифровка верна. успешная расшифровка

Главный недостаток симметричной схемы. Для шифрования и для расшифровки используется один и тот же пароль (ключ). Значит, его нужно как-то безопасно передать получателю. Если канал передачи перехватят — вся защита теряется. Именно эту проблему решает асимметричное шифрование (раздел 3–4).

3. Генерация пары ключей GPG и обмен публичными ключами

3.1. Ключ пользователя kali

gpg --full-generate-key

Параметры: тип RSA and RSA, длина 3072 бит, срок действия — бессрочно, имя kali, e-mail kali@gmail.com.

pub   rsa3072 2026-10-13 [SC]
      B32902B6A5DBEBED88C3B16BD9626E6A3EC8D21F
uid                      kali <kali@gmail.com>
sub   rsa3072 2026-10-13 [E]

Экспорт публичного ключа в бронированный (ASCII-armored) файл:

gpg --export --armor "kali@gmail.com" > ~/my_public.asc
cat ~/my_public.asc

-----BEGIN PGP PUBLIC KEY BLOCK-----
mQGNBGrOnDYBDACrNilXQm8rL8XdAmA4jtblelGssJdqiSC7//cbEQzgtZW7irt2
... (сокращено) ...
=aPWv
-----END PGP PUBLIC KEY BLOCK-----

my_public.asc создан — этот файл передаётся напарнику.

3.2. Ключ напарника (пользователь partner)

Для эмуляции второго участника в системе создан пользователь partner:

sudo adduser partner
su - partner

Первые попытки gpg --full-generate-key от имени partner падали с ошибкой agent_genkey failed: Отказано в доступе (конфликт gpg-agent между пользователями). Проблема решена пакетной генерацией с явным паролем:

gpg --batch --pinentry-mode loopback --passphrase 'Partner2026test' \
    --quick-generate-key "Partner <partner1@gmail.com>" rsa3072 default never

gpg --list-keys
pub   rsa3072 2026-10-13 [SC]
      984B2C0E8DE92074578B65E941671001F203F45B
uid         [  абсолютно ] Partner <partner1@gmail.com>

Изначально у ключа не было подключей для шифрования (только [SC]). Добавлен подключ шифрования:

gpg --batch --pinentry-mode loopback --passphrase 'Partner2026test' \
    --quick-add-key 984B2C0E8DE92074578B65E941671001F203F45B rsa3072 encrypt never

gpg --list-keys
pub   rsa3072 2026-10-13 [SC]
      984B2C0E8DE92074578B65E941671001F203F45B
uid         [  абсолютно ] Partner <partner1@gmail.com>
sub   rsa3072 2026-10-13 [E]

Экспорт публичного ключа напарника:

gpg --export --armor "partner1@gmail.com" > ~/partner_public.asc
sudo cp /home/partner/partner_public.asc ~/partner_public.asc
sudo chown kali:kali ~/partner_public.asc

3.3. Импорт публичного ключа напарника

3.4. Установка доверия ключу напарника

Изначально ключ помечен [ неизвестно ], из-за чего шифрование отклонялось (Непригодный открытый ключ). Доверие выставлено вручную:

gpg --edit-key "partner1@gmail.com"
gpg> trust
Ваше решение? 5
Вы действительно хотите сделать этот ключ абсолютно доверенным? (y/N) y
gpg> quit

gpg --list-keys
pub   rsa3072 2026-10-13 [SC]
      984B2C0E8DE92074578B65E941671001F203F45B
uid         [  абсолютно ] Partner <partner1@gmail.com>
sub   rsa3072 2026-10-13 [E]
Итог раздела. Публичные ключи обоих участников импортированы, ключ напарника помечен как доверенный и пригоден для шифрования ([E]).

4. Асимметричное шифрование для напарника

4.1. Шифрование файла публичным ключом напарника

gpg --encrypt --armor -r "partner1@gmail.com" ~/report.txt
Файл '/home/kali/report.txt.asc' существует. Записать поверх? (y/N) y

ls -la ~/report.txt.asc
-rw-rw-r-- 1 kali kali 756 окт 14 00:20 /home/kali/report.txt.asc

Содержимое зашифрованного файла:

cat ~/report.txt.asc

-----BEGIN PGP MESSAGE-----
hQGMA/vLmmIHSB6EAQv/brqjlq3wDRQ8klH9Bq/+qsukN09nOG/TolpCzxwyR3xV
... (сокращено) ...
=6Jym
-----END PGP MESSAGE-----

report.txt.asc — зашифрован публичным ключом напарника. Расшифровать его может только напарник своим закрытым ключом.

4.2. Передача файла напарнику

sudo cp ~/report.txt.asc /home/partner/
sudo chown partner:partner /home/partner/report.txt.asc

4.3. Расшифровка напарником

Первая попытка упала с сбой расшифровки с открытым ключом: Отказано в доступе — из-за конфликта gpg-agent между пользователями. После перезапуска агента от имени partner:

gpgconf --kill all
sudo pkill -u partner gpg-agent
su - partner
gpg-agent --daemon --homedir /home/partner/.gnupg
gpg --decrypt ~/report.txt.asc

gpg: encrypted with rsa3072 key, ID FBCB9A6207481E84, created 2026-10-13
      "Partner <partner1@gmail.com>"
(расшифрованный текст отчёта)

напарник расшифровал файл своим закрытым ключом

Почему общий секрет не нужен (в отличие от раздела 2).
В симметричной схеме обе стороны должны заранее знать один и тот же секретный ключ — его надо как-то передать, и это узкое место.
В асимметричной схеме у напарника есть пара ключей: публичный и закрытый. Публичный ключ можно свободно раздавать — он не секретный. Я шифрую файл его публичным ключом, а расшифровать может только он своим закрытым, который никуда не передаётся. Поэтому согласовывать общий секрет заранее не требуется.

5. Электронная подпись и проверка

5.1. Подпись подлинного документа

gpg --sign --armor ~/report.txt

gpg --verify ~/report.txt.asc
gpg: Подпись сделана ... [GNUPG:] GOODSIG ...
gpg: Действительная подпись от "kali <kali@gmail.com>"

подпись действительна — документ не изменялся, подпись сходится.

5.2. Изменение документа и проверка старой подписью

Изменяем исходный документ на один символ, подписываем заново и пробуем проверить старой/чужой подписью:

echo "." >> ~/report.txt
gpg --sign --armor ~/report.txt
gpg --verify ~/report.txt.asc   # проверка подписи, сделанной для ДРУГОГО содержимого

gpg: ПОДПИСЬ НЕВЕРНА
gpg: подпись выполнена ... но содержимое не совпадает
[GNUPG:] BADSIG ...

подпись недействительна — при любом изменении документа проверка ломается, что и подтверждает контроль целостности и авторства.

Вывод. Электронная подпись одновременно подтверждает авторство (ключ подписанта) и целостность (документ не изменён). Один изменённый байт — и gpg --verify сообщает о недействительной подписи.

Замечания по ходу работы (для протокола).
  • GUI-режим ettercap -G в данной сборке Kali падает (GTK/gdk-pixbuf), для практики не требуется.
  • Конфликт gpg-agent между пользователями решён перезапуском агента от имени нужного пользователя (gpgconf --kill all, pkill -u <user> gpg-agent, gpg-agent --daemon --homedir ...).

sha256sum /etc/passwd

# вернуть файл (если нужно):

ДЗ-2. Симметричное шифрование с надёжным паролем

openssl enc -aes-256-cbc -pbkdf2 -salt -in file.txt -out file.enc
openssl enc -aes-256-cbc -pbkdf2 -d -in file.enc -out file.dec
diff file.txt file.dec

Сдать: команды + доказательство совпадения (diff пуст).

ДЗ-3. Экспорт/импорт публичного ключа и шифрование

gpg --export --armor "ваш@email" > my_public.asc

Сдать: my_public.asc, file.txt.asc, вывод расшифровки у напарника.
